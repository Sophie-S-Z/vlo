# Vlo: instructions for coding agents

This file is for every coding agent that works in this repository: OpenAI Codex, Claude Code and others.
`CLAUDE.md` loads this file, so both tools follow the same rules. Change a rule here, not in `CLAUDE.md`.

The product owner is Praneel (GitHub `Sophie-S-Z`). Praneel works in this repository with Codex and with
Claude Code, sometimes on the same day. Read "Work beside the other agent" before you start a change.

## 1. Rules that you must always obey

### 1.1 Supabase: the owner runs every live change

The owner runs every change to the live Supabase database. Do not apply a migration. Do not run SQL that
writes, changes or deletes data or schema on the live database. A read-only query for measurement is
permitted.

When a change needs a migration or an SQL run, give the owner all of this:

1. The file path in `supabase/migrations/`, and the full SQL in one block to copy.
2. Where to run it: Supabase dashboard, project "Vlo", SQL Editor, New query.
3. What the SQL changes, in a few short lines, and if old app versions keep working.
4. Any prompt that Supabase shows (for example a warning about a destructive statement), and the answer.
5. A read-only check query to run after it, and the result to expect.
6. The order of the steps, for example "run the SQL first, then merge the pull request".

A new migration that the new app needs must go live before its pull request merges. Vercel deploys `main`
at once, so a merge before the SQL breaks the live app.

### 1.2 Secrets

- Never commit, print or ask for the Supabase service key, the database password or a writer's AI key.
- The committed `.env` holds only public values: the Supabase URL, the publishable key and a switch.
  Row level security and the grants of the migrations keep the tables closed.
- Name an environment variable in text. Never write its value in a pull request, an issue or a log.

### 1.3 No AI attribution lines

Do not put "Generated by", "Generated with", "Requested by" or a similar AI attribution line in code,
comments, commit messages, pull request titles or pull request text. Do not put a model name in them.

### 1.4 Writing style

Praneel reads every message, commit and document in ASD-STE100 Simplified Technical English. The docs,
help text and interface text of this repository use it too. Obey these rules:

- Use the active voice. Write short sentences: 20 words at most for an instruction, 25 for a description.
- Put one instruction in each sentence. Use the present, past or future tense.
- Use one word for one idea. Write "start", and not "begin", "commence" or "initiate".
- Do not use em dashes, filler words ("really", "actually"), hedges or performed enthusiasm.
- Start a reply with the result or the question. Give a recommendation, not a long list of options.

### 1.5 Ask before these steps

Ask the owner before you spend money, delete data, change a production setting (Vercel, Supabase, GitHub,
a domain), publish something, add a package, or merge a pull request. A new package needs its name, its
license, its size and the reason (`docs/VLO_SPEC.md` section 0, rule 7).

## 2. What Vlo is

Vlo is a local-first writing app for novels, memoirs and poetry. Every word stays in the writer's browser
(IndexedDB). It works offline as a PWA and needs no account to write. An optional account syncs projects
between devices with sealed (end-to-end encrypted) blobs. Vlo sends nothing else unless the writer asks for
an AI request, a share link, feedback, a weekly usage report or a WordPress.com draft. The one exception is
an anonymous daily count that Settings can turn off.

- Production: https://vlo-eight.vercel.app/ (Vercel deploys `main`). Each pull request gets a Vercel preview.
- Marketing site: https://vlo-landing-page.vercel.app/ (not in this repository).
- Product spec: `docs/VLO_SPEC.md`. The user guide is the Help page (`src/features/help/help.ts`).
- In the app, "Codex" is a feature: the story bible of a project (`src/features/codex`). It has no relation
  to OpenAI Codex.

## 3. Stack

- Node 22 (`.nvmrc`, `engines`). npm with `package-lock.json`. Use `npm ci`, not `npm install`.
- Vite 8, React 19, TypeScript 6 (strict, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`),
  React Router 8. Path alias `@/` is `src/`.
- Tailwind CSS 4, Radix UI, `class-variance-authority`, Motion, lucide-react icons.
- Editor: TipTap 3 on ProseMirror, with Yjs documents (`y-indexeddb`) for each item.
- Storage: Dexie 4 on IndexedDB (`src/lib/db.ts`).
- In the browser: Transformers.js and WebLLM (AI and voices), harper.js (grammar), pdf-lib, pdfjs, docx,
  jszip, MathLive, MiniSearch.
- Server: Supabase (Postgres functions called over REST, Auth with an email code or Google), one Vercel
  function (`api/geo.ts`) and one Cloudflare Worker with an R2 bucket (`workers/files`).
- Tests: Vitest with jsdom and `fake-indexeddb`, PGlite for the SQL, Playwright with axe-core.

## 4. Where things are

- `src/app`: routes (`routes.tsx`), the app shell, preferences, themes and error screens.
- `src/features/<feature>`: one folder for each feature, such as `editor`, `export`, `share`, `sync`,
  `account`, `ai`, `binder`, `board`, `codex`, `voice` and `workshop`.
- `src/lib`: shared code. `db.ts` is the database, `ydocs.ts` the item documents, `net.ts` the network
  module, `privacy.ts` the private names, `workerCall.ts` the worker helper.
- `src/ui`: shared interface parts (Radix wrappers, buttons, dialogs).
- `api/geo.ts`: the Vercel function that gives a rough place for the daily count.
- `workers/files`: the Cloudflare Worker of the sync file store in R2 (ADR 0014). The owner deploys it with
  Wrangler (`docs/files-setup.md`).
- `supabase/migrations`: the SQL, numbered `NNNN_name.sql`.
- `tests/unit`: Vitest tests. `tests/e2e`: Playwright tests, named after a user story where one exists.
  `tests/fixtures`: the poem, memoir and novel fixtures and the 100,000-word generator.
- `scripts`: the bundle size check, the license check, the icon and data builders.
- `docs`: the spec, `STATUS.md` (with the older entries in `history.md`), the plans (`docs/plans/phase-N.md`), the ADRs (`docs/adr/NNNN-title.md`),
  the setup guides and the policy texts.

## 5. Commands

| Command                | What it does                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------- |
| `npm ci`               | Installs the packages from the lock file.                                           |
| `npm run dev`          | Starts the development server.                                                      |
| `npm run build`        | Builds the app into `dist/`.                                                        |
| `npm run preview`      | Serves `dist/` on port 4173.                                                        |
| `npm run typecheck`    | Runs TypeScript on every project (`tsc -b`).                                        |
| `npm run lint`         | Runs ESLint, with the network rule.                                                 |
| `npm run format:check` | Checks the Prettier style. `npm run format` fixes it.                               |
| `npm test`             | Runs the unit tests with Vitest.                                                    |
| `npm run e2e`          | Builds the app and runs the Playwright tests (only Chromium on a local machine).    |
| `npm run size`         | Checks the initial JavaScript against the 250 KB gzip budget. Run it after a build. |
| `npm run licenses`     | Checks the package licenses and writes `docs/licenses.md`.                          |

Before each push, run `typecheck`, `lint`, `format:check`, `test`, `build` and `size`. CI runs the same
checks. Run one test file with `npx vitest run tests/unit/<name>.test.ts`, or one browser test with
`npx playwright test tests/e2e/<name>.spec.ts`.

Notes on the test runs:

- The browser tests need a Playwright browser: `npx playwright install --with-deps chromium`.
- The unit tests run with no Supabase project, so no unit test reaches the live database
  (`vitest.config.ts`). The browser tests use a fake project (`playwright.config.ts`).
- The SQL tests run every migration in PGlite, a real Postgres in WebAssembly. A new migration needs a test.
- Known failure: `tests/unit/docx-libreoffice.test.ts` fails its equation test where LibreOffice is
  installed without LibreOffice Math. It passes in the CI export files job. Do not try to fix it.
- Known flaky browser tests: the PWA update test, some Firefox page loads and two board timing tests.
  `docs/STATUS.md` ("Open") gives the details. CI retries a failed test once.
- The full Playwright suite takes about 30 minutes on one worker. Run the files that your change touches.

## 6. CI and deploy

- `.github/workflows/ci.yml` runs on each pull request: the checks, the export files job (LibreOffice,

## 7. Supabase

- One free Supabase project, "Vlo". The browser calls Postgres functions (`/rest/v1/rpc/...`) with the
  publishable key. Each table has row level security with no policies, so only the functions reach the
  tables. Each function checks the shape of its input and has a fixed `search_path`.
- The server stores only cipher text for share links and sync. It never sees a word of a writer's text.
- The free plan limits matter: a 500 MB database and 5 GB of egress each month. Migration 0017 and
  ADR 0008 give the sync limits. Migration 0018 and ADR 0014 move sync files to Cloudflare R2. The owner
  page warns at 70% of 500 MB.
- `pg_cron` runs the daily cleanups (migrations 0003 and 0005).

| -------------------------- | ---------------------------------------------------------------------- |

| `0002_usage.sql`           | Opt-in usage reports (counts and bands only).                          |
| `0003_cleanup.sql`         | The daily cleanup of old shares.                                       |
| `0004_limits.sql`          | Input checks and caps for a public key.                                |
| `0005_sync.sql`            | Sealed sync between a writer's devices.                                |

## 8. Rules for every change

- Only `src/lib/net.ts` may make a network request. An ESLint rule enforces it, and the network log records
  each request. A new host goes in `HOSTS` in `net.ts` and in the CSP in `vercel.json`. A unit test compares
  the two.
- A new network purpose needs an entry on the privacy page (`src/features/policy/privacy.ts`, and the same
  words in `docs/privacy.md`). Raise its `version` and set its `date`. A unit test fails until it has one.
- Pen mode sends nothing and loads no AI code. The US09 test checks a 60-second session.
- No third-party script, font, analytics or tracking pixel. Fonts come from the app's own files.
- A copy that leaves the writer's text (an export, a share link, an AI request or a web search) puts the
  aliases of `privatePeople` in place of the real names.
- Poems keep every space, indent and stanza break in every format.
- A change to stored data needs a new Dexie version in `src/lib/db.ts`. A change to the item document
  raises `DOC_SCHEMA` (`src/features/editor/docSchema.ts`). A change to the backup raises `BACKUP_VERSION`
  (`src/features/backup/file.ts`). Old data must still open.
- Keep the initial JavaScript under 250 KB gzip. Load large code on first use with a dynamic import.
- Accessibility: WCAG AA contrast, keyboard use and screen reader labels. The axe tests must pass.
- Use test-driven development for logic. Check a change to the interface in a real browser.
- Ship no placeholder code, no "TODO later" comments and no fake data in the interface.
- Record each architecture decision as a short ADR in `docs/adr/NNNN-title.md`.
- Keep `docs/STATUS.md` current: add a dated entry at the top of "Done", and update "Open" and "Decisions".

## 9. Git and pull requests

- `main` is the production branch. Do not push to `main`. Open a pull request, and let the owner merge it.
- Make one branch for each task. Codex uses `codex/<short-name>`. Claude Code uses `claude/<short-name>`.
- Commit messages: one short line in the imperative ("Add page setup: margins and page numbers"), then a
  blank line and short lines on what changed and why, if necessary.
- A pull request text has a summary, "Changes", "Checks" (each command and its result) and, if the change
  needs SQL, "Deploy order". Give each fact that the owner must act on.
- Assign the pull request to `Sophie-S-Z`.

## 10. Work beside the other agent

Codex and Claude Code work on the same repository. Neither tool sees the other's chat.

1. Before you start, run `git fetch origin` and start your branch from the newest `origin/main`.
2. Look at the open pull requests. Do not change files that an open pull request changes, unless the owner
   tells you to.
3. Read the top of `docs/STATUS.md`. It is the shared record of what is done and what is open.
4. When you finish, write what you did, what is open and each decision in `docs/STATUS.md`. The other agent
   reads only the repository.
